# DisputeAI

**DisputeAI** — нативное Android-приложение для совместного решения задач несколькими языковыми моделями.

Модели сначала предлагают независимые варианты, затем критикуют и улучшают решения друг друга, а отдельная модель формирует итоговый ответ.

## Как это работает

1. В первом цикле модели отвечают независимо и не видят ответы друг друга.
2. Со второго цикла начинается общая дискуссия и взаимная критика.
3. Спор может завершиться раньше заданного максимума, когда участникам больше нечего существенно добавить.
4. После завершения отдельная модель результата формирует конечный ответ.

По умолчанию установлено до **10 циклов**. Для результата используется независимый первый цикл, **последние 3 цикла** и реплики пользователя. При необходимости можно включить **весь контекст дискуссии**.

## Основные возможности

- две и более независимо настраиваемые модели-участника;
- отдельные настройки сценария для каждого чата;
- глобальные профили API, которые можно выбирать для моделей разных чатов;
- отдельная модель результата;
- OpenAI-совместимые API, Anthropic и Gemini;
- OpenRouter web search и capability-aware reasoning;
- streaming, Markdown и таблицы;
- вложения и история чатов;
- редактируемые промпты и индивидуальные цвета моделей;
- пауза, продолжение и остановка дискуссии;
- foreground service с уведомлением во время активной работы;
- настройки фоновой работы и оптимизации батареи.

## Сценарии использования

DisputeAI можно использовать с обычными промптами по умолчанию. Для специализированной задачи участникам можно назначить разные роли — тогда они будут рассматривать одну проблему с разных сторон.

**Куда вставлять промпты:** в боковой панели нажмите **⋮** у нужного чата → **Настройки чата**. Каждый чат хранит собственный набор моделей, ролей, промптов и параметров дискуссии. API-ключи и адреса подключений настраиваются отдельно в **О приложении и API**, после чего в карточке модели выбирается нужное API-подключение. Промпты первого и последующих циклов можно оставить стандартными: они уже отвечают за независимый первый цикл и взаимную критику дальше.

Если участников только два, используйте первые две роли. Названия моделей не имеют значения: роли можно назначать любым подключённым моделям.

<details>
<summary><strong>Технический аудит и поиск ошибки</strong></summary>

Подходит для разбора бага, архитектурной проблемы, лога, участка кода или неудачного технического решения.

**Участник 1 — разработчик**

```text
Ты опытный разработчик. Ищи корневую техническую причину проблемы. Анализируй код, архитектуру, состояние, потоки данных и зависимости. Предлагай конкретные исправления, а не общие советы.
```

**Участник 2 — строгий ревьюер**

```text
Ты строгий code reviewer. Ищи ошибки в предложенных решениях, скрытые зависимости, регрессии, неправильные предположения и случаи, которые могли быть пропущены. Не соглашайся без проверки.
```

**Участник 3 — тестировщик**

```text
Ты инженер по тестированию. Рассматривай задачу через реальные сценарии использования, граничные случаи, ошибки пользователя, нестабильную сеть, фоновые процессы и восстановление после сбоев.
```

**Модель результата**

```text
Собери технический вывод из всей дискуссии. Отдели подтверждённые причины от предположений. Дай наиболее вероятную причину, минимальное безопасное исправление и список проверок после изменения. Избегай ненужного рефакторинга.
```

Пример запроса: `После сворачивания приложения загрузка иногда обрывается. Вот лог и соответствующий код. Найдите точную причину и безопасное исправление.`

</details>

<details>
<summary><strong>Выбор покупки, сервиса или технического решения</strong></summary>

Подходит для сравнения телефонов, ноутбуков, VPS, приложений, API, библиотек и других вариантов, где одного списка характеристик недостаточно.

**Участник 1 — практик**

```text
Оцени варианты с точки зрения реального повседневного использования. Приоритет: удобство, надёжность, цена владения и отсутствие лишних проблем.
```

**Участник 2 — технический эксперт**

```text
Сравни варианты по характеристикам, ограничениям, совместимости, производительности и запасу на будущее. Выявляй маркетинговые характеристики, которые мало влияют на реальное использование.
```

**Участник 3 — скептик**

```text
Ищи причины не выбирать каждый вариант: скрытые недостатки, плохую поддержку, ограничения, переплату, слабые места и возможные проблемы после покупки или внедрения.
```

**Модель результата**

```text
Выбери лучший вариант под задачу пользователя. Не делай компромисс ради компромисса. Назови победителя, объясни, почему он лучше остальных, и укажи случаи, когда стоит выбрать другой вариант.
```

Пример запроса: `Сравните эти три VPS для автоматизации публикаций. Важны стабильность, российский IPv4, 4 ГБ RAM и минимальная цена.`

</details>

<details>
<summary><strong>Редактура статьи или большого текста</strong></summary>

Подходит для статьи, поста, инструкции, описания проекта или другого текста, который нужно проверить не только на ошибки, но и на качество подачи.

**Участник 1 — редактор**

```text
Ты редактор интернет-издания. Улучшай структуру, логику, темп текста, заголовок, вступление и понятность. Убирай воду, повторы и тяжёлые формулировки.
```

**Участник 2 — обычный читатель**

```text
Ты обычный читатель, а не редактор. Отмечай места, где становится скучно, непонятно, слишком долго или возникает желание закрыть текст. Оценивай, действительно ли материал даёт обещанную пользу.
```

**Участник 3 — фактчекер**

```text
Проверяй утверждения на логические ошибки, преувеличения, сомнительные факты и необоснованные выводы. Отделяй факты от мнений и предположений.
```

**Модель результата**

```text
Подготовь итоговую редакторскую версию. Сохрани смысл и стиль автора, но исправь слабые места, найденные участниками. Не превращай текст в безликий шаблонный материал.
```

Пример запроса: `Проверьте приложенную статью перед публикацией. Нужны сильное начало, понятная структура, отсутствие повторов и сохранение авторского стиля.`

</details>

<details>
<summary><strong>Планирование новой функции или проекта</strong></summary>

Подходит перед разработкой новой функции, крупной переделкой интерфейса, миграцией или другим изменением, где важно заранее увидеть стоимость и риск регрессии.

**Участник 1 — архитектор**

```text
Спроектируй решение с минимальной сложностью. Учитывай существующую архитектуру, зависимости и дальнейшее сопровождение. Не создавай абстракции без необходимости.
```

**Участник 2 — разработчик**

```text
Оцени практическую реализацию: какие части кода придётся менять, какие данные нужны, какие состояния появятся и где вероятны ошибки. Предпочитай небольшие последовательные изменения.
```

**Участник 3 — специалист по регрессиям**

```text
Главная задача — найти, что новое изменение может сломать. Проверяй обратную совместимость, сохранённые данные, старые сценарии, фоновые процессы и взаимодействие с уже работающими функциями.
```

**Модель результата**

```text
Составь реалистичный план реализации по этапам. Для каждого этапа укажи цель, что меняется и что обязательно проверить. Предпочитай минимальные изменения с низким риском регрессии.
```

Пример запроса: `Нужно добавить в Android-приложение пресеты дискуссий. Предложите архитектуру и план реализации так, чтобы не сломать существующие настройки.`

</details>

<details>
<summary><strong>Решение спорного вопроса: «за», «против» и независимая оценка</strong></summary>

Подходит, когда у решения есть сильные аргументы с обеих сторон: менять ли архитектуру, добавлять ли функцию, переходить ли на другой сервис, выпускать ли версию сейчас.

**Участник 1 — позиция «за»**

```text
Защищай вариант ЗА. Найди сильнейшие аргументы в его пользу, практическую выгоду и долгосрочные преимущества. Не игнорируй недостатки, но оценивай, можно ли ими управлять.
```

**Участник 2 — позиция «против»**

```text
Защищай вариант ПРОТИВ. Ищи риски, цену сложности, скрытые последствия, альтернативы и причины оставить всё как есть.
```

**Участник 3 — независимый аналитик**

```text
Ты независимый аналитик. Не занимай заранее ни одну сторону. Проверяй аргументы обеих сторон, ищи ложные дилеммы и варианты, которые позволяют получить пользу без крайних решений.
```

**Модель результата**

```text
Не выбирай сторону по количеству аргументов. Оцени их силу. Дай решение, условия, при которых оно верно, основные риски и критерии, при которых решение стоит пересмотреть.
```

Пример запроса: `Стоит ли сейчас переводить приложение с одного API-провайдера на универсальную OpenAI-совместимую настройку, или лучше оставить текущую архитектуру?`

</details>

## Безопасность

API-ключи хранятся локально в зашифрованном виде. Ключ шифрования защищён **Android Keystore**. Резервное копирование приватных данных приложения отключено.

## Установка

Готовые стабильные APK находятся в разделе **Releases**.

Требуется Android 7.0 или новее (`minSdk 24`).

## Сборка

```bash
gradle :app:assembleDebug
```

GitHub Actions проверяет сборку при изменениях.
